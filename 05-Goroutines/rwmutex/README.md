# rwmutex — бонус

Задача выходит за рамки основной лекции и даёт 100 бонусных баллов.

Есть общие данные и два вида пользователей: читатели только смотрят на них,
писатели меняют. Читатели могут работать одновременно друг с другом, но
писателю нужен исключительный доступ.

Реализуйте блокировку чтения и записи с помощью каналов:

```go
func New() *RWMutex
func (rw *RWMutex) Lock()
func (rw *RWMutex) Unlock()
func (rw *RWMutex) RLock()
func (rw *RWMutex) RUnlock()
```

`New()` создаёт объект без взятых блокировок; поддержка нулевого значения
не нужна. Объект нельзя копировать после начала использования.

- `Lock` ждёт, пока не будет ни читателей, ни другого писателя, и занимает
  блокировку для одного писателя. `Unlock` освобождает её.
- `RLock` ждёт окончания записи. Одновременно читать могут несколько горутин.
  Каждая из них завершает чтение вызовом `RUnlock`.
- Пока хотя бы один читатель владеет блокировкой, писатель войти не может.
- Новые читатели могут присоединяться к текущим даже при ожидающем писателе:
  приоритет писателей и справедливость очереди в этой учебной задаче не требуются.

Переход от чтения к записи без освобождения блокировки не поддерживается.
Корректные пары вызовов гарантируются вызывающим кодом. Паники при неправильном
`Unlock`/`RUnlock` и владение конкретной горутиной проверять не нужно.

Идея такого разделения есть в [sync.RWMutex](https://pkg.go.dev/sync#RWMutex),
но здесь требуется только описанный выше контракт. Использовать `sync`
(включая `sync/atomic`) в реализации нельзя.

Ожидание должно блокировать горутину на канале. Цикл, который непрерывно
проверяет состояние, даже с `Sleep` или `Gosched`, не подходит.

Перед решением подумайте: какое состояние нужно хранить, когда вошёл первый
читатель и когда выходит последний? Все изменения этого состояния должны
быть синхронизированы. Достаточно каналов; готовые mutex не нужны.

Проверка из корня репозитория:

```shell
go test ./05-Goroutines/rwmutex/...
go test -race ./05-Goroutines/rwmutex/...
```
